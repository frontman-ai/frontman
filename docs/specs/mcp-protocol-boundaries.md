# Spec: MCP Protocol Boundaries

## Objective

Complete PR #1490's MCP 2026-07-28 migration without weakening Frontman's task isolation.
Accept the full core MCP request shape at the wire boundary, refine it into supported protocol and
Frontman-specific states, and return the specification-defined error for each failed refinement.

## Commands

- Protocol tests: `make test` in `libs/frontman-protocol`
- Browser MCP tests: `make test` in `libs/frontman-client`
- Server tests: `mix test test/frontman_server_web/channels/task_channel/mcp_initializer_test.exs test/model_context_protocol_test.exs test/protocols/mcp_contract_test.exs`
- Schema check: `make check-schemas` in `libs/frontman-protocol`
- ReScript format: `make rescript-format` from repository root
- Elixir format: `mix format --check-formatted` in `apps/frontman_server`

## Project Structure

- `libs/frontman-protocol/src/FrontmanProtocol__MCP.res`: core MCP wire types, refined request types,
  and protocol errors.
- `libs/frontman-client/src/FrontmanClient__MCP.res`: browser MCP server request handling.
- `libs/frontman-client/src/FrontmanClient__MCP__Server.res`: exact Frontman-owned response builders.
- `apps/frontman_server/lib/model_context_protocol.ex`: Frontman MCP client request builders.
- `apps/frontman_server/lib/frontman_server_web/channels/task_channel/mcp_initializer.ex`: discovery
  and tool-catalog consumer.

## Code Style

Represent validation stages with variants and `Result`, not booleans or optional fields that permit
contradictory states:

```rescript
type requestError =
  | InvalidParams(string)
  | UnsupportedProtocolVersion({requested: string, supported: array<string>})
  | MissingRequiredCapability({requiredCapabilities: clientCapabilities})

switch validateRequest(params) {
| Ok(validRequest) => handle(validRequest)
| Error(error) => sendProtocolError(error)
}
```

Incoming schemas accept specification-defined optional and extension fields. Outgoing Frontman
builders may remain narrow because Frontman controls those values.

## Testing Strategy

- Add failing browser-server tests before changing request parsing.
- Use official MCP examples as independent fixtures rather than validating only against schemas
  generated by Frontman types.
- Test malformed metadata, unsupported versions, missing capabilities, valid empty capabilities,
  optional client identity, public cache scope, optional server identity and tool description, and
  paginated tool lists.
- Preserve tests for task mismatch, string JSON-RPC IDs, arbitrary structured content, and handler
  failures.

## Boundaries

- Always preserve `ai.frontman/execution-context` task and call correlation for tool execution.
- Always parse protocol version as a string before checking support.
- Always accept empty and unknown client capabilities at the core MCP boundary.
- Always use `-32022` with `supported` and `requested` for unsupported versions.
- Always use `-32021` with `requiredCapabilities` when execution needs an undeclared capability.
- Ask first before adding a JSON Schema validation dependency.
- Never restore legacy `initialize` compatibility in this change.
- Never use `Obj.magic` or broaden types with unchecked casts.

## Success Criteria

- A valid `server/discover` request with empty capabilities and no `clientInfo` succeeds.
- An unsupported protocol version returns `-32022` and required error data.
- A Frontman tool call without execution-context capability returns `-32021` and required error data.
- A malformed Frontman execution-context payload returns `-32602`.
- Only a task-authorized tool-call type can reach tool execution.
- Discovery and tool-list consumers accept legal optional/open MCP fields.
- All pages from a paginated tool list are accumulated before initialization completes.
- Existing Frontman browser behavior and task-isolation tests remain green.
- Generated schemas and committed schema files agree.
