# MCP 2026-07-28 HTTP And Security Traceability

This is the current implementation matrix. Frontman uses sessionless Streamable HTTP from the browser to JavaScript framework and WordPress servers at `POST /mcp`; the browser HTTP client also accepts standard SSE. Both Frontman server implementations emit synchronous JSON until a real streaming producer exists. JavaScript bearer and WordPress session/capability/nonce checks are application authentication, not MCP OAuth. The OAuth rows use the following role-specific inventories and focused absence vectors; those vectors prove that OAuth behavior is absent, not that Frontman conforms to the OAuth requirements:

- `SRC-JS-RESOURCE`: `FrontmanCore__MCP__HttpSecurity`, `FrontmanCore__MCP__Endpoint`, `FrontmanCore__MCP__AdapterSecurity`, and the active Next.js, Astro, and Vite adapters implement only `/mcp` plus application 401/403 decisions.
- `SRC-WP-RESOURCE`: `Frontman_Auth`, `Frontman_Router`, and `Frontman_MCP` implement the exact WordPress `/mcp` route plus session, capability, and nonce decisions.
- `SRC-BROWSER-CLIENT`: `FrontmanClient__MCP__Client.connect`, `post`, and `responseJson` issue MCP POSTs and decode JSON/SSE responses; they contain no challenge parser, metadata discovery, registration, redirect, or token exchange path.
- `V-CORE-NO-CHALLENGE`: `FrontmanCore__MCP__HttpSecurity.test.res` vector `maps authentication and authorization failures after Origin acceptance` proves application 401/403 responses omit `WWW-Authenticate`.
- `V-JS-NO-OAUTH`: `mcp-blackbox.test.ts` vectors `does not expose OAuth protected-resource metadata routes` and `enforces Origin, authentication, preflight, and media policy` prove real Next.js/Astro/Vite processes expose neither protected-resource metadata nor `WWW-Authenticate` on application 401/403.
- `V-WP-NO-OAUTH`: `McpTest.php::test_application_failures_have_no_authentication_challenge_or_side_effects` proves unit-level 401/403 challenge absence; `RouterTest.php::test_protected_resource_metadata_routes_are_absent` covers root, `/mcp`, and scoped metadata paths; `scripts/test-wordpress-plugin-runtime.sh` vectors `WordPress MCP missing authentication` and `WordPress MCP invalid nonce` exercise runtime application 401/403; and `wordpress-playground-blackbox.test.ts` vector `enforces Playground session, nonce, Origin, preflight, and media policy` proves Playground 401/403 challenge absence.
- `V-BROWSER-NO-FOLLOWUP`: `FrontmanClient__MCP__OAuthAbsence.test.res` vector `does not follow a hostile resource_metadata challenge` proves exactly one original `/mcp` POST and zero metadata-discovery, registration, or token follow-up requests.

Transport-specific evidence is indexed in `../capability-support.md` and configuration in `../endpoint-auth.md`.

## Decision Notes

These are boundary findings and current Frontman decisions, not additional MCP normative requirements.

1. **Missing Origin:** The specification requires Origin validation on all incoming connections but explicitly mandates 403 only when `Origin` is present and invalid. Frontman requires exactly one valid allowlisted Origin for every browser-facing `/mcp` request; absent, malformed, opaque `null`, multiple, or unlisted values receive 403 before body processing. Supporting non-browser callers requires a separately approved authenticated policy.
2. **Host and DNS:** MCP expressly requires Origin validation; it does not separately state an uppercase Host/authority validation requirement. Trusted-proxy handling, Host validation, DNS/IP checks, and rebinding-resistant deployment remain Frontman security policy and must not be represented as MCP normative text.
3. **Request media and statuses:** The researched Streamable HTTP section normatively fixes response media types and the client's dual Accept header. It does not state an uppercase request `Content-Type: application/json`, 415, 406, OPTIONS, CORS, `Vary: Origin`, `Allow`, body-size, or nesting-depth requirement. Frontman enforces those where documented as local HTTP and security policy; the matrix does not attribute them to MCP.
4. **Validation order:** Frontman's route-independent boundary implements Origin, authentication/authorization decision, media negotiation, limits, UTF-8/JSON, envelope/direction, headers, protocol metadata, method parameters, tool selection, argument validation, then execution. Active adapters must preserve this order. It is a Frontman safety decision supporting the normative requirements, not normative text itself.
5. **No legacy HTTP shape:** The initial implementation has no initialization handshake, GET stream, MCP session, DELETE termination, `Mcp-Session-Id`, SSE resumability, `Last-Event-ID` behavior, or independent server JSON-RPC requests. GET and DELETE receive 405 under the source recommendation and Frontman policy.
6. **SSE deferral:** The browser client must consume interoperable JSON and SSE. Frontman servers emit synchronous JSON until a real producer needs progress or streaming; SSE-only server requirements remain deferred rather than claimed complete.
7. **WordPress authentication:** WordPress retains authenticated sessions, required capability checks, nonce validation on every MCP POST, exact Origin validation, private cache scope, and authorization-specific cache keys. These controls do not activate or satisfy the MCP OAuth protected-resource profile.
8. **OAuth boundary:** All OAuth authorization, discovery, registration, token, scope, PKCE, redirect, and OAuth-specific security rows are N/A because MCP authorization is optional and Frontman does not support it. Remote framework access requires a separately approved complete OAuth feature; Frontman must not expose an incomplete bearer-token or fake-metadata subset.
9. **Cancellation limits:** Frontman enforces the documented 60-second idle timeout where applicable, 10-minute absolute timeout, and 4,096 Phoenix late-response IDs retained for 15 minutes. Transport-specific ownership and exact boundary vectors are recorded in `implementation-limits.md`; WordPress does not claim PHP-side disconnect cancellation or the Node/Web timers.
