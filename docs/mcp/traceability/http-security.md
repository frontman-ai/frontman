# MCP 2026-07-28 HTTP And Security Traceability

This Phase 0 matrix inventories normative requirements; it does not claim runtime implementation. Frontman initially uses sessionless Streamable HTTP from the browser to framework and WordPress servers at `POST /mcp`. Framework servers initially serve local development, WordPress retains its authenticated session, capability, and nonce controls, and both return synchronous JSON until a real streaming producer exists. MCP OAuth authorization is not implemented initially. If remote framework access is later required, Phase 10 requires a separate feature implementing the complete protected-resource flow rather than a partial bearer-token substitute.

## Decision Notes

These are boundary findings and planned Frontman decisions, not additional MCP normative requirements.

1. **Missing Origin:** The specification requires Origin validation on all incoming connections but explicitly mandates 403 only when `Origin` is present and invalid. Frontman requires exactly one valid allowlisted Origin for every browser-facing `/mcp` request; absent, malformed, opaque `null`, multiple, or unlisted values receive 403 before body processing. Supporting non-browser callers requires a separately approved authenticated policy.
2. **Host and DNS:** MCP expressly requires Origin validation; it does not separately state an uppercase Host/authority validation requirement. Trusted-proxy handling, Host validation, DNS/IP checks, and rebinding-resistant deployment remain Frontman security policy and must not be represented as MCP normative text.
3. **Request media and statuses:** The researched Streamable HTTP section normatively fixes response media types and the client's dual Accept header. It does not state an uppercase request `Content-Type: application/json`, 415, 406, OPTIONS, CORS, `Vary: Origin`, `Allow`, body-size, or nesting-depth requirement. Phase 2/10 may enforce those as HTTP and security policy; the planned response/status matrix must not attribute them to MCP.
4. **Validation order:** Frontman plans Origin, authentication/authorization, media negotiation, limits, UTF-8/JSON, envelope/direction, headers, protocol metadata, method parameters, tool selection, argument validation, then execution. This ordering is a Frontman safety decision supporting the normative requirements, not normative text itself.
5. **No legacy HTTP shape:** The initial implementation has no initialization handshake, GET stream, MCP session, DELETE termination, `Mcp-Session-Id`, SSE resumability, `Last-Event-ID` behavior, or independent server JSON-RPC requests. GET and DELETE receive 405 under the source recommendation and Frontman policy.
6. **SSE deferral:** The browser client must consume interoperable JSON and SSE. Frontman servers emit synchronous JSON until a real producer needs progress or streaming; SSE-only server requirements remain deferred rather than claimed complete.
7. **WordPress authentication:** WordPress retains authenticated sessions, required capability checks, nonce validation on every MCP POST, exact Origin validation, private cache scope, and authorization-specific cache keys. These controls do not activate or satisfy the MCP OAuth protected-resource profile.
8. **OAuth boundary:** All OAuth authorization, discovery, registration, token, scope, PKCE, redirect, and OAuth-specific security rows are not applicable initially because MCP authorization is optional and Frontman does not support it. Remote framework access requires a separately approved complete OAuth feature; Frontman must not expose a partial bearer-token or fake metadata subset.
9. **Cancellation limits:** Phase 0 fixes a 60-second idle timeout, 10-minute absolute timeout, and 4,096 late-response IDs retained for 15 minutes. Rows marked planned do not assert that current adapters enforce those limits, propagate disconnect, or stop current tools; exact boundary vectors are assigned in `implementation-limits.md`.
